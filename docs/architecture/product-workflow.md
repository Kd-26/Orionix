# Canonical customer workflow

This workflow is the product contract. “Execution boundary” means the customer host or isolated provider worker. Control-plane receipt is restricted to the allowlist in [customer data boundaries](../security/customer-data-boundaries.md).

| Step | Input | Output | Owner | Trust boundary | Failure behavior | Sensitive data leaves execution? |
|---:|---|---|---|---|---|---|
| 1. Create organization/project | Identity and tenant metadata | Tenant-scoped organization and project IDs | Control plane: tenancy | User → control plane | Reject unauthorized or duplicate requests; audit without secrets | Not applicable; no execution environment yet |
| 2. Connect/select GPU environment | Existing-host enrollment choice or provider target | Connection target with credential references | Control plane: environment registry | Customer/control plane or provider API | Validate authority; store only secret references; make no allocation implicitly | Provider account credentials remain control-plane-side |
| 3. Enroll/start worker | One-time enrollment grant or narrowly scoped job credential | Authenticated persistent agent or ephemeral worker | Agent supervisor and provisioning backend | Control plane ↔ execution boundary | Expire/revoke failed grants; terminate orphaned provider compute | Only enrollment proof and redacted identity metadata |
| 4. Discover environment | Typed discovery command | Provider, node, accelerator, topology, and software facts with provenance | Execution backend and discovery subsystem | Inside execution boundary; redacted report crosses outward | Return partial/unknown facts explicitly; never infer support; clean up temporary probes | Only redacted or hashed capability metadata |
| 5. Inspect model | Local model reference and revision policy | `ModelSpec` and revision fingerprint | Model inspector | Model store → execution boundary | Fail closed on unreadable/ambiguous revision; do not transfer weights | Redacted model metadata and fingerprint only |
| 6. Collect constraints | Workload distribution, SLO, quality, cost, and experiment budget | Versioned optimization request | Control plane and workload/quality boundary | Customer → control plane; sensitive datasets stay local | Reject incomplete, contradictory, or unbounded requests | Distribution/constraint metadata may; prompts/datasets do not |
| 7. Evaluate capability | Model, cluster, software, engine profile, constraints | Representability and engine-compatibility decision with reasons | Capability evaluator plus engine adapter | Control-plane policy using signed/redacted facts | Unknown evidence cannot become compatible; return remediation | No new raw data |
| 8. Communicate status | Compatibility decision and certification registry entry | Certified, experimental, or unsupported user decision | Control plane: support policy | Control plane → customer | Block unsupported; require explicit warning acceptance for experimental | No |
| 9. Run controlled baseline | Approved typed launch, workload generator, limits | Baseline observations and provenance | Benchmark subsystem under execution backend | Inside execution boundary | Enforce timeout/cost/OOM limits; stop engine; preserve partial evidence | Aggregates may; raw requests/responses/logs do not |
| 10. Generate candidates | Baseline, discovered capabilities, engine capabilities, constraints | Finite feasible candidate set | Candidate generator | Control-plane planning boundary | Emit no candidate if compatibility is unproven; explain pruning | No execution-sensitive payloads |
| 11. Execute optimization | Candidates and hard experiment budget | Candidate observations and terminal budget state | Optimizer coordinator and benchmark subsystem | Control plane coordinates; execution backend runs | Stop new candidates at any limit; cancel and clean up idempotently | Aggregate measurements and redacted state only |
| 12. Evaluate constraints/quality | Candidate results and local evaluation data | Pass/fail results with reasons and confidence | Constraint evaluator and execution-side quality evaluator | Quality data remains execution-side | Reject missing/invalid evidence; never silently waive constraints | Quality summary may; dataset/prompts/completions do not |
| 13. Rank results | Valid measured candidates and explicit objective | Pareto set and provisional recommendation | Result ranker | Control-plane policy boundary | Return insufficient-evidence state when no candidate qualifies | No new sensitive data |
| 14. Confirm finalists | Pareto finalists and confirmation policy | Independent longer-run evidence | Benchmark subsystem | Inside execution boundary | Require configured run count; reject unstable finalists; clean up | Aggregates only |
| 15. Create report/capsule | Confirmed evidence, configuration, fingerprints, constraints | Report and layered Execution Capsule metadata | Reporting and capsule subsystem | Control plane metadata; binary artifacts stay execution-side | Fail if evidence or integrity metadata is incomplete; never overstate support | Approved report/metadata only; architecture binaries stay local by default |
| 16. Export configuration | Recommended configuration and target format | Reproducible serving/deployment files without secret values | Deployment exporter | Execution/control plane → customer review surface | Validate digest, schema, and required secret names; no live mutation | Customer-approved export only |
| 17. Review/apply manually | Report, capsule, export, warnings | Customer approval and externally applied configuration | Customer/operator | Product → customer production boundary | Product records approval/rejection; no automatic fallback deployment | Controlled by customer |
| 18. Schedule revalidation | Approved profile, drift policy, and schedule | Manual-approval revalidation request | Control plane scheduler | Control plane ↔ execution boundary | Do not run without valid authorization/budget; isolate failures from active deployment | Same allowlist as original workflow |

All commands are typed, versioned, authenticated, expiring, idempotent, and allowlisted. State transitions and cleanup tolerate at-least-once delivery. Arbitrary remote shell execution and automatic production mutation are prohibited.
